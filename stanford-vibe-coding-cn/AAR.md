## 三、做对了什么（深度洞察）

### 洞察 1：先找"入口站"，再辐射全网

**做法：** 第一轮搜索没有直接搜"Stanford Vibe Coding 讲义"，而是先搜"课程官网"，找到了 themodernsoftware.dev 这个入口站，然后从它的外链辐射到 GitHub 仓库、韩语翻译站、客座讲师信息。

**为什么有效：** 入口站是信息密度最高的地方。一个官方课程站 = 十几个分散信息点的集合。从入口站往外找，比全网散搜效率高 3 倍。

**可复用经验：** 以后做类似课程翻译项目，第一步永远是"找到官方课程主页"，而不是先搜资料。

### 洞察 2：二手解读反向定位一手来源

**做法：** 掘金文章（中文二手）提到了 CS146S，我没有止步于此，而是顺着提到的课程编号和讲师名（Mihail Eric），反向找到了官网和 GitHub。

**为什么有效：** 二手内容往往已经帮你做了信息筛选和提炼。你只需要顺着线索找到源头，就能获得一手内容 + 二手解读的双重价值。

**可复用经验：** 遇到优质二手解读时，不要只消费二手内容——花 5 分钟找到一手源头，长期收益更大。

### 洞察 3：术语表前置，是质量的关键杠杆

**做法：** 翻译之前先花 15 分钟建 glossary.md，把核心术语的译法定下来，然后所有翻译都对照这个表。

**为什么有效：** 翻译质量的最大杀手不是"翻得不准"，而是"前后不一致"。同一个词前面叫"智能体"后面叫"代理"，读者会困惑。术语表一次性解决一致性问题，投入产出比极高。

**可复用经验：** 任何超过 3 篇文档的翻译项目，都应该先建术语表再开工。

## 四、哪里做得不够（根因分析）

### 问题 1：视频字幕和幻灯片完全没碰

**表面现象：** 只翻译了文字大纲，视频讲座字幕和幻灯片 PDF 为 0。

**直接原因：** 时间和精力集中在文字页面抓取和翻译上，没有安排多媒体内容的时间。

**根本原因：**
- 启动时的范围定义不够细——"课程资料"到底包含哪些类型？没有一开始列清楚
- 对"多媒体资料获取难度"估计不足——以为抓网页就够了，低估了视频字幕的工程量
- 缺少"内容类型清单"作为 checklist，导致漏项

**改进方案：** 下次项目启动时，先列一个"内容类型 checklist"：
- [ ] 课程主页文字
- [ ] 教学大纲
- [ ] 幻灯片 PDF
- [ ] 讲座视频字幕
- [ ] GitHub 作业代码
- [ ] 阅读材料列表
- [ ] 客座讲师资料

每一项标上优先级和预计工作量，避免做到一半才发现漏了大块内容。

### 问题 2：人工校对比例偏低，母语级润色缺失

**表面现象：** AI 初译 + 术语校验就发布了，没有做深度人工润色。

**直接原因：** 时间有限，优先保证"有"而不是"精"。

**根本原因：**
- 对"质量可控"的标准设定偏低——以为术语对了就是质量好
- 没有区分"信息准确"和"表达流畅"两个质量维度
- 缺少母语级审校环节

**改进方案：** 建立三级质量标准：
1. **L1 信息准确**：内容没翻错、术语统一、格式完整（当前已达到）
2. **L2 表达流畅**：语句通顺、无翻译腔、符合中文技术文档习惯（下一步目标）
3. **L3 母语地道**：由资深技术译者润色，达到出版级质量（长期目标）

### 问题 3：管线自动化只做了一半

**表面现象：** 有抓取脚本和翻译任务生成脚本，但翻译本身还是手动喂给 AI 的。

**直接原因：** 没有接入大模型 API，翻译环节还是半自动。

**根本原因：**
- 对"管线自动化"的预期偏保守——觉得"有脚本辅助"就算自动化了
- 没有把端到端的自动化作为目标——从抓取到翻译到校验一键跑完

**改进方案：** 下一阶段接入 LLM API（如 OpenAI / Claude / 豆包 API），实现：
```
配置文件 → 自动抓取 → 自动分段 → 自动翻译 → 自动术语校验 → 自动合并输出
```

真正做到"改配置 = 换一门课"。

## 七、三条最重要的经验沉淀

> **经验 1：先建管线，再填内容。**
> 一开始就急着翻译几篇文章，是最常见的错误。先花 1-2 小时把"怎么找、怎么翻、怎么校、怎么存"的流程想清楚，后面的效率是指数级提升的。

> **经验 2：入口站 > 全网散搜。**
> 信息获取的第一优先级是找到官方入口站。一个入口站 = 十几个信息点。从入口往外辐射，比全网搜效率高得多。

> **经验 3：下一批用户是第一评审。**
> 项目做得好不好，不是看你做了多少，而是看下一批人能不能在 5 分钟内用起来。USAGE.md 的价值，不亚于翻译内容本身。
